Two sessions, one repository

Continue a reviewed change in a new chat

Imagine a small Python CSV exporter. In the first session, you ask an assistant to add a tab-separated output option while preserving the existing comma-separated output. The assistant proposes the change and a regression test for the comma output. You review both, then run the configured Kit checks and record their result with the work state.

Before changing chats, generate and validate the successor package. In the second session, the next assistant reads the package and repository state before extending the exporter. If the old-output test fails, the test gate reports the failure. A passing check confirms only its defined conditions; it cannot decide whether the export format meets your needs.

You decide whether the change meets the requirement and whether to approve a merge or release. A local coding agent or controller can use the same repository record.

Who it serves

Maintainers of continuing projects

Solo maintainers and small teams working with AI on Git-backed software or documentation, particularly across long sessions, reviews and releases. Python is a reference profile; equal maturity across all toolchains is not claimed.

Why use it

Durable context and bounded actions

Repository state replaces dependence on chat memory. Manifest-backed workflows expose effects, checks and evidence. Generated handoffs make the next session inspectable.

Mechanisms and tradeoffs

What it costs

Explicit process takes work

Adoption requires Git knowledge, maintained contracts, useful tests and review. More state files and closeout steps are real overhead. Green gates do not prove correct requirements or defect-free software.

Read the limits

Why

Repository Memory

Long LLM projects lose time when context lives in chat history. The Kit makes the repository the durable project memory: current state, handoff packages, command manifests, gates, reports and release evidence are inspectable before new work starts.
