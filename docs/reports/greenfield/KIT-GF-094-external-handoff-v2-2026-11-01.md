# KIT-GF-094 — external successor content projection

Status: implementation validation in progress; fixed_in: unreleased.
Owner scope: 2026-11-01, stage 1, external workspaces only. No release,
production migration or merge is authorized by this report.

## Observation and historical baseline

At Kit 1.1.10, generated successor freshness compares generated HEAD with current
HEAD or accepts refresh-only descendants. A squash changes HEAD even when none
of the handoff inputs changes. The externally supplied historical comparison
for an external desktop controller, 2026-10-24 through 2026-10-31, records 19 of
38 merged PRs as successor refreshes and 37% of CI minutes. A line-filter
inspection found only Git identity and generation time changes in five files.
These are historical supplied measurements, not new measured performance gains.

## Implementation and contract difference

`DPA-GENERATED-SUCCESSOR-HANDOFF-PROJECTION-v1` remains the global self-hosting
contract. External dispatch uses
`DPA-GENERATED-SUCCESSOR-HANDOFF-PROJECTION-v2`. Its exact differences are:

- Durable identity is frozen source content, packaged command manifest, Kit and
  generator versions, repository identity and output settings. Runtime Git/time
  fields are absent. Regenerated bytes alone decide content validity.
- The digest and individual input hashes explain freshness versus integrity;
  neither can override differing bytes.
- All eight durable outputs are generator-owned. External-only refresh can
  migrate manifest and ignore entry in the same governed repair PR.
- Only the final-head identity rule changes. The other security rules retain
  their v1 contents, and exact HEAD checking moves to the ignored runtime object.
  Approvals, CI, release gates and signed plans retain exact commit binding.

See [the published contract](../../reference/EXTERNAL_HANDOFF_V2.md), its runtime
fixture and the source diff for the precise v1/v2 ownership and identity fields.
An external v1 package never passes under the new Kit. Migration sets the
independent minimum to 2. The normal signed update plan binds and writes the
new projection with the adoption. Existing post-merge repair creates one
migration PR if needed. Same-version artifact replacement cannot silently
remove v2 support.

## Proof and limits

The local machine contract uses real branches, commits, squash merges, pushes
and a bare origin: unchanged inputs yield READY with no refresh; changed input
without regeneration fails; regenerated input passes after squash; runtime
HEAD is exact, run IDs differ, and repeated durable generation leaves no diff.
Tests block renderer filesystem/process/network access and cover complete input
digests, golden output, minimum versions, corruption and migration errors.
Pure-route tests snapshot all repository files, including ignored files, index,
refs and local evidence, on successful and failing checks with network blocked.

External tests in successor, transfer, checks and init were deliberately updated
because they previously expected v1 HEAD identity or no initial package. Their
self-hosting expectations are retained. The direction renderer adds the existing
canonical-source notice so its generated Markdown meets documentation coverage.
No historical C4 report is rewritten.

The owner additionally approved the complete external v1-HEAD consumer scan.
The external documentation audit now shares byte validation; the bootstrap
renderer dispatches by workspace mode and its validator checks the complete v2
projection. Init applicability and work start share first-cycle detection and
retain explicit-missing and corrupt-package failures. PR/CI heads, return v1
proof, self-hosting audit/render paths and commit-bound closeout receipts are
separate authorities and retain their commit binding. GF-015 and the external
release-resolution fixture regenerate after deliberately changing captured

GF-084 now explicitly removes four package files in its disposable fixture to

Final gate results and noneditable-wheel machine evidence belong in the paired

## Net workflow complexity, old versus new

For a product PR with unchanged captured inputs, versioned handoff changes go
from five historically observed files to zero; successor PRs/CI runs go from
one product plus one refresh to one product only. This is a deterministic
workflow count, not a measured CI-time saving. Changed authority still requires
regeneration and the normal gates. The external state machine gains one
one-time NEEDS_PROJECTION_MIGRATION transition; READY no longer requires a
refresh-only descendant. Existing repair states remain for actual drift.

No recurring human step is added. The exceptional installation return requires
owner approval. New focused modules isolate projection, update preview and
return evidence; the local machine fixture uses an installation double. V2 has
one durable contract version and one ignored runtime schema. The receipt and
append-only ledger bind the rare return to an exact adoption rather than adding
a general installer or downgrade switch. Tests and existing deterministic
renderers provide validation; DCO adds no advantage to these bounded artifacts.
